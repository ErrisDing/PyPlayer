## 1. 目标

让播放列表能显示每首曲目的时长、艺人、专辑，并把这份数据按库持久化，使第二次启动不必重新提取。

可核对的成功判据：

1. 三列在**两张主题**下均可见、可辨认，时长右对齐，长文本按 delegate 现有省略规则收缩而不是撑破行。
2. 冷库：文件表先出现在列表里，元数据在后台逐行补上；补上之前那几列显示"未取到"记号，**不是** `0:00`、不是空白、不是英文名。
3. 标签里确实没有艺人/专辑的文件，显示"取不到"记号，且与判据 2 的"未取到"记号**长得不一样**。
4. 同一库第二次打开：不重新提取，三列直接来自缓存。
5. 换过的文件（`mtime` 或 `size` 变了）被重新提取；没变的文件**不会**被每次启动重啃。
6. 提取失败/不支持的文件被记为"已试过"，不会每次启动重试。
7. 老缓存（`version: "1.0"`）仍能读出文件表并被就地升级为 2.0，**不会**触发整库重扫。
8. 全量 `discover -s tests` 不新增失败（唯一失败仍是 main 既有的 `test_multiple_libraries_display`）。

## 2. 边界：为什么只有这些

本批**只改数据获取与缓存契约 + 视图渲染**，以下三件明确不做，且不是"砍需求"而是换批：

- **按列排序、按内容筛选**：需要"显示行 ↔ 队列 node 行"的映射层，那是批次 6 的契约。批次 3 已把"显示行 ≠ node 行"这条事实在 `PlaylistView` 上用测试钉住（`tests/test_playlist_actions.py` 的 folder 队列用例），正是为此留的接口。把排序塞进本批会同时改两层。
- **NCM 进自动提取**：`service/tools/ncm.py` 提取时会**生成解密代理文件**，是有副作用、按文件耗时的动作。给整库每个 `.ncm` 悄悄生成一份代理不是"显示一列"该有的代价。首版 NCM 走现有播放时按需取的路径。**因此 NCM 必须归入"取不到"而不是"未取到"**：它不在任何待办队列里，永远不会有"稍后就填上"的时刻 —— 见 §4.1 对排除格式的规定。否则一个排除掉的格式会伪装成"还在加载"。
- **库总时长/曲目数聚合**：数据本批之后确实齐了，但"放在哪"是界面决定（浮层？表头？侧栏？），且它与每库曲目数同属侧栏信息。混进来会让数据批夹带界面改动，正是批次 2 拆出 B5 时避开的那种混。

**做的三件边界内的事**（用户 2026-10-20 批准，均按控制器推荐）：

1. 修 `core/metadata.py:55-56` 的英文兜底 `"Unknown Artist"` / `"Unknown Album"` —— 提取层改为"没有就是 `None`"，由展示层决定画什么。
2. NCM 不进自动 sweep（见上）。
3. 不做聚合（见上）。

## 4. 必须钉死的决策

### 4.1 "未取到"与"取不到"是两个状态，用一个键表达

`CachedFile` 新增**一个**可选键 `md`，值为 `{artist, album, duration}`（各项可为 `null`）。语义：

- **`md` 整个缺失** = 还没提取（pending）。
- **`md` 存在、某项为 `null`** = 提取过、标签里确实没有（unknown）。
- **`md` 存在且有值** = 已知。

不用三个平铺字段，因为 `null` 无法同时表达"没取"和"取到但为空"——那正是本批要区分的两件事（判据 2、3）。同理，"`md` 存在"本身就是"已试过"的记录，所以坏文件不会被每次启动重试（判据 6）。

**排除格式也算"已试过"**：`md` 只有两种来源 —— 真去提取，或**明确决定不提取**。NCM（§2）这类被排除的格式，扫描时直接写 `md`（三项 `null`），于是它落在"取不到"而不是"未取到"。规则一句话：`md` 缺失 ⟺ 有东西在等着取；没有东西会来取的，必须写 `md`。

### 4.2 `duration <= 0` 一律存成 `null`

提取器现在把"读不到"塌成 `0.0`（§3）。缓存里 **`0.0` 不允许出现**：`duration <= 0` 归一为 `null`。理由：合法音频时长不可能为 0，因此这个归一不丢信息；而把 0 当"已知"会让界面画出 `0:00`，直接违反判据 2。

### 4.3 版本升 `2.0`，但读侧同时接受 `1.0`

`CACHE_VERSION` 升到 `"2.0"`；`load_cache` 改为接受 `{1.0, 2.0}` 两个版本，把 1.0 的条目当作"`md` 缺失"就地升级（下次写回落 2.0）。**不得**沿用今天"版本不等即整份作废"的行为——那会让每个已存在的库在升级当天被判"没缓存"，白白重扫文件表（判据 7）。写侧只写 2.0。

### 4.4 写回按批，不按条

sweep 每完成一批（数量与节流阈值由实现阶段量测后定，见 §8 的探针要求）或收尾时**一次**写回。逐条写 = 每条都 `json.dump` 整个文件。

### 4.5 切库取消，用代号而不是共享队列

`sweep` 绑定一个"库代号"，切库时代号自增；回调发现结果属于旧代号即丢弃。**不得**靠"清空队列"实现——`QThreadPool` 的已入队任务撤不干净，且共享池上会出现上一库的结果写进当前库缓存这种脏数据（见 §10 风险 1）。

### 4.6 失效判据分两层

- **文件表**：沿用现有根目录 mtime 粗判（本批不改它，改了是另一件事）。
- **元数据**：逐文件比 `size_bytes` + `modified_time`；任一不同即视为该文件的 `md` 失效。"刷新媒体库"（图标栏已有此动作）强制重扫全库元数据：**忽略 §4.6 的 `size`/`mtime` 比对**，对每个非排除格式重新提取（不是清掉 `md` 等 sweep 再填，也不是只挑失败的那些）。

### 4.7 表头接管现有那行，且必须过双向守卫

三列需要表头解释，否则空白列无从判断（这是选 A 方案的理由）。表头接管 `#playlistHeader` 那行 QLabel。**注意批次 2 立下的双向对账**：`objectName` ↔ QSS 规则两个方向都会查（"有名字没规则"与"有规则没佩戴者"都算问题）。所以新表头的每个名字要么真带样式、要么按 `KNOWN_DEAD_SELECTORS` 那条路登记为**有记录的**决定，不许留未登记残留。

### 4.8 展示记号走文案，不走英文字面量

`—`（取不到）与 `⋯`（未取到）两个记号进 `locales/interface/main.{zh_CN,en_US}.properties`，键按既有按控件命名前缀（批次 3 裁定 R5 的口径，**不要**并入退役中的 `menu.*` 块）。展示层不得再出现 `"Unknown Artist"` 一类英文字面量。

### 4.9 列的数据由谁携带

三列读的是**扫描结果一路带上来的那份元数据**，不是 `Track`。原因具体：`Track.duration` 的类型是
`float = 0.0`（`core/library_manager.py:228`），它的 `0.0` 与 §4.2 要消灭的那个歧义同源——
"没填"和"真是 0"同一个值。若 delegate 从 `Track` 读时长，§4.1 的两态在到画的那一刻就又塌成一片。

落点在实现阶段定（`DisplayEntry` 或扫描产物的同路载体都行），约束只有两条：**画一行时不做第二次查找**
（不按路径去问缓存或文件系统），以及携带者必须能表达"无值"而不是 0。`DisplayEntry` 现有字段语义不改，
队列契约也不改（批次 5 的地盘）。

## 5. 数据流

```
图标栏「打开文件夹」/「刷新」
        ↓
scan_directory → 文件表（含 mtime/size）→ 列表立刻显示（三列空=未取到）
        ↓
MetadataService.sweep(paths, library, generation)   ← 复用已有 QThreadPool
        ↓ 逐条 extract_metadata（不读封面）
内存缓存 + 待写批次
        ↓ 按批（§4.4）
LibraryCacheManager.save_cache(version 2.0，条目带 md)
        ↓ 每条完成
PlaylistModel 行内更新（时长/艺人/专辑）→ delegate 重画该行
```

下次打开同库：缓存直接带 `md` → 列表出来就是满的，sweep 只对 §4.6 判定失效的文件跑。

## 6. 错误处理

- **提取抛异常/格式不支持**：仍写 `md`（各项 `null`），即"已试过"，不重试、不弹窗（后台动作没有"发起动作的按钮"可挂进度以外的反馈）。
- **文件在提取过程中被删**：写回前重比对 `size/mtime`，不一致即跳过该条并记入待重扫集合；**不得**把已删文件的元数据写进新快照。
- **缓存写失败**（磁盘/权限）：内存结果照常生效，列表不受影响；本批**不新增**错误弹窗通道，沿用现有失败上报路径。
- **正在播放那首被 sweep 更新**：不得触发 `NowPlayingStrip` 重建导致标题闪烁；封面仍走播放时的异步路径，本批不缓存封面。

## 8. 测试

契约与状态机（离屏可测）：

- **缓存 round-trip**：2.0 读写；1.0 读入→文件表可用→写回落 2.0；两版都不触发重扫。
- **三态矩阵**：pending / 取到空 / 取到有值，各自的显示值与 `md` 形状。
- **归一**：提取器返回 `duration=0.0` → 缓存存 `null` → 画 `—`（判据 2 的直接钉子）。
- **失效矩阵**：mtime 变、size 变、都没变、提取失败四类，各自"是否重新提取"。
- **切库代号**：起 sweep A → 切到 B → A 的结果回来，断言 A 的结果**没有**写进任何缓存、也没有刷 B 的行。
- **按批写回**：计数写回次数，断言不随文件数线性增长（防 O(n²) 回归）。
- **不阻塞主线程**：sweep 期间事件循环仍可响应。

视图渲染（按批次 3 的规矩测像素，不写 item QSS 规则——那类规则在本仓永不渲染，批次 2、3 各踩过一次）：

- 三列在两主题下的列位置、时长右对齐、省略号收缩、pending/unknown 两个记号可辨。
- 表头接管后 `#playlistHeader` 相关的 objectName/QSS 双向守卫仍绿。
- 渲染矩阵新增一帧：带满元数据的列表（含一个 pending、一个 unknown 行），供目视。

**实现前必须量的探针**（不得照抄本文档的数字）：写回批大小、单文件提取耗时（各格式）、sweep 与用户点击并发时的行为。探针脚本不入库。

i18n：新键在两份 locale 都存在，且不引入硬编码英文字面量（沿用批次 1 的守卫形状）。
